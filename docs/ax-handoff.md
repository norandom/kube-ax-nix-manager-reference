# Handoff: deploy and fan out AX workflows on the kube-ax cluster

You are a Claude Code session helping the operator move their AX workflows, which currently run on a
local **kind** cluster with Agent Substrate, onto the **kube-ax** cluster described here, and run them
fanned out across its nodes. Everything you need, including credentials, is in this document. Treat
the credentials as secrets: don't print them in full, commit them to a public place, or send them anywhere
other than the cluster API below.

## 1. Facts about the target cluster

- **Kubernetes:** k3s v1.36.4 on 2 NixOS nodes, each 4 vCPU / 8 GiB.
  - `kube-01` (10.0.0.63): control plane + workloads.
  - `kube-02` (10.0.0.58).
  - API: `https://10.0.0.63:6443`, reachable on the operator's LAN (10.0.0.0/24) only.
- **Agent Substrate main `715f2daa` (v0.3.0-34)** in `ate-system`. **AX v0.3.1** in `ax-system` (ax-server, ax-controller, Redis).
- **Sandbox class: gVisor only.**
  - AX v0.3.1 hard-codes `gvisor-default`.
  - There is no micro-VM SandboxConfig; don't plan for one.
- **Workers:** two gVisor WorkerPools in `ax-workers`, one per node: `compute-kube-01`, `compute-kube-02`, label `pool: ax-compute`.
  - Limits are shared by all actors on the worker. AX sets no per-task resources.
  - Each worker: **3 GiB / 3 vCPU**, and it runs **one task at a time** (Substrate per-worker actor limit 1).
  - A busy worker is skipped, so concurrent engines land one per node.
  - **A task submitted while both workers are busy FAILS** (AX v0.3.1 doesn't queue). Keep **≤ 2 tasks in
    flight** and resubmit failures.
- **Scheduling:** 1 AX Task = 1 actor. Substrate picks a worker **uniformly at random**.
  - AX has **no** fan-out, retries or parallelism fields.
  - Fan-out = submit N Tasks; roughly half land on each node.
- **Snapshots:** S3 on the operator's rustfs at `http://10.0.0.54:9000`, bucket `k3s-ate-snapshots` (AX uses `gs://k3s-ate-snapshots/ax/`; the scheme is ignored).
- **Registry:** `ghcr.io/norandom`. There is no in-cluster registry and no kind `localhost:5001` registry.
- **Telemetry:** OpenObserve at `http://10.0.0.54:40002`, streams `k3s_logs`, `k3s_events`, `k3s_traces`, `k3s_<metric>`.
- **Egress (automatic, nothing to do on your side):** each task gets the host list of its **name prefix**
  within ~1 s of starting (longest prefix wins, HTTPS on 443 only):
  - `ousast-engine-search-exec-*`: any public host;
  - `ousast-engine-search-verify-*`, `-search-probe-*`, `ousast-engine-pass-*`: files.because-security.com;
  - `ousast-engine-replay-*`: files.because-security.com and github.com;
  - any other `ousast-engine-*` name: **no egress**; names outside `ousast-engine-`: any public host.
  - The operator's egress-watcher attaches the policy; the gateway's "no policy yet" deny cache is 2 s.
    **Retry the first outbound connection for up to 60 s.**
  - Blocked for everyone: other ports, plain HTTP, LAN and cluster-internal addresses.
  - New prefixes or hosts: ask the operator; don't create egress policies yourself.
- **Task completion:** AX v0.3.1 never marks a task finished; the phase stays `Running` after the command exits.
  - Read the result and exit code from the worker log. In the operator repo that's `just ax-logs TASK`; elsewhere,
    filter `kubectl -n ax-workers logs <worker-pod>` for JSON lines with `labels."ate.actor.name" == TASK`.
  - Then `ax delete task`. The operator's reaper deletes `ousast-engine-*` tasks 10 min after their command
    exited, as a safety net only.
- **Submitting:** treat `ResourceExhausted "no free workers available"` as "retry in 2–5 s" for up to a minute
  (both workers busy, or Substrate's ~1 s golden copy of a new task holds one). Count runs only from log lines
  with `ate.atespace == default`.
- **Files inside a task:** `/` and `/workspace` are on disk; **`/tmp` is RAM** and counts against the
  worker's 3 GiB. Set `TMPDIR=/workspace/tmp`.
- **Images:** all images in rotation together ≤ ~9 GiB unpacked (node cache cap 10 GiB); shared base,
  code in the last layer, rebuild only on demand.

**What this identity can do** (ServiceAccount `ax-system/ax-deployer`):

- `services` get, `pods` get/list, and `pods/portforward` create in `ax-system`. That's all the `ax` CLI needs; it

- `pods` and `pods/log` get/list/watch, and `workerpools.ate.dev` get/list/watch, in `ax-workers` (read-only).

**What it cannot do:**

- create, change or delete any Kubernetes object;
- read secrets;
- touch `ate-system`;
- `ax ssh` (that tunnels into `ate-system`).

If the migration needs any of these, for example new WorkerPools, ActorTemplates, Secrets or
namespaces, **stop and ask the operator**. Don't try to work around the RBAC.

AX itself has **no authentication**. Whoever can reach ax-server controls every task. Never expose the
port-forward beyond localhost.

## 4. Differences from kind that will break workflows unless handled

| In kind | On kube-ax | Do this |
|---|---|---|
| Images pushed to `localhost:5001` / `kind-registry:5000` | atelet pulls task images **anonymously** from public registries | Push to `ghcr.io/norandom/<name>`, make the package **Public** (`https://github.com/users/norandom/packages/container/<name>/settings`), reference it **by digest** |
| Default task image `gcr.io/ax-substrate/ate-images/ax-task-runner` | that image is private (401) | Use `ghcr.io/norandom/ax-task-runner@sha256:c1c4951ee672ef77f845b2742124f6106b300e433426fde1768381ad5d55fad7` or images built `FROM ghcr.io/norandom/ax-task-runner:v0.3.1` |
| Custom images without the runner | every task image must contain `/usr/local/bin/ax-task-runner` | `FROM ghcr.io/norandom/ax-task-runner:v0.3.1`, then add your deps |
| `AX_SNAPSHOTS_BUCKET` / `BUCKET_NAME=ate-snapshots` (kind rustfs) | already set server-side to `k3s-ate-snapshots` | Don't set buckets in Tasks |
| `kubectl` with cluster-admin on kind | restricted deployer identity | Use `ax` for tasks; ask the operator for anything else |
| Micro-VM demos (`demo-*-microvm`) | not installed | gVisor only |
| Workspace `goal` with an LLM (`GEMINI_API_KEY` secret) | no LLM secret exists on kube-ax | Use `spec.command` tasks, or ask the operator to create `gemini-api-secret` in the atespace namespace |
| Unlimited local CPU | 2 workers × 3 vCPU / 3 GiB, one task each | Size shards; set BLAS/OMP threads to 2 |

## 5. Migration procedure

1. **Inventory the kind setup:** the operator's Task / Workspace / Model YAMLs, the images they use, and how work
   is split today. Note any `localhost`/kind registry references, `gs://` or bucket settings, LLM keys, and
   micro-VM usage.
2. **Images:** for each task image, rebuild it `FROM ghcr.io/norandom/ax-task-runner:v0.3.1` (plus its deps)
   for `linux/amd64` and push it to `ghcr.io/norandom/<name>:<tag>`. Get the digest with
   `podman push --digestfile …` or `crane digest`. Ask the operator to make each package public, then verify
   anonymous access:

   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' "https://ghcr.io/token?service=ghcr.io&scope=repository:norandom/<name>:pull"   # 200 = public
   ```

3. **Rewrite the Tasks:**
   - `metadata.atespace: default` (or the operator's choice);
   - `spec.image: ghcr.io/norandom/<name>@sha256:…`;
   - `spec.command` for the work;
   - `spec.env` for parameters.
   - Remove kind-specific fields.
4. **Smoke test one Task**, then check where it ran:

   ```yaml
   apiVersion: ax.io/v1alpha1
   kind: Task
   metadata: {name: smoke-1, atespace: default}
   spec:
     image: "ghcr.io/norandom/ax-task-runner@sha256:c1c4951ee672ef77f845b2742124f6106b300e433426fde1768381ad5d55fad7"
     command: ["sh", "-c", "echo host=$(hostname) cpus=$(nproc); head -c 268435456 /dev/zero | sha256sum"]
   ```

   ```bash
   ax apply -f smoke.yaml && ax watch task smoke-1
   ax get tasks                                  # WORKER-IP column
   kubectl -n ax-workers get pods -o wide        # map worker IP -> node
   ax delete task smoke-1
   ```

5. **Fan out:** generate one Task per shard, each with `TASK_INDEX` / `TASK_COUNT` env vars, and apply them in a
   single multi-document YAML:

   ```bash
   IMG=ghcr.io/norandom/<name>@sha256:<digest>; N=4
   for i in $(seq 0 $((N-1))); do cat <<YAML
   ---
   apiVersion: ax.io/v1alpha1
   kind: Task
   metadata: {name: job-$i, atespace: default}
   spec:
     image: "$IMG"
     env: [{name: TASK_INDEX, value: "$i"}, {name: TASK_COUNT, value: "$N"}]
     command: ["python", "/opt/job/job.py"]
   YAML
   done | ax apply -f -
   ax get tasks
   ```

   In the operator's repo the same thing is `just ax-fanout NAME COUNT IMAGE cmd…`.
6. **Verify distribution:** both `compute-kube-01-*` and `compute-kube-02-*` should have hosted tasks. Check
   with `kubectl -n ax-workers get pods -o wide` and the WORKER-IP values. Placement is random, so small batches
   can be uneven; that's expected.
7. **Clean up:** run `ax delete task <name>` for every submitted task. Task state lives in a non-persistent Redis,
   so keep the Task YAML in the operator's repo, not only in AX.

## 6. Sizing guidance for compute-heavy shards

**Engine tasks (JVM): use exactly these flags.** Each worker runs one engine (3 GiB / 3 vCPU):

```text
-Xms1700m -Xmx1700m -XX:MaxMetaspaceSize=256m -XX:ReservedCodeCacheSize=128m
-XX:MaxDirectMemorySize=256m -Xss512k -XX:ActiveProcessorCount=2 -XX:+UseG1GC
```

- About 2.3–2.5 GiB per engine including the gVisor sandbox; 2 GC/compiler threads on a 3-vCPU worker.
- A larger heap (beyond ~2.2 GB) no longer fits the 3 GiB worker; the worker's cgroup would OOM-kill the engine.
- **One engine per worker**, so ≤ 2 concurrent engine tasks in total. A 3rd submitted while both run fails
  with "no free workers available". The dispatcher keeps ≤ 2 in flight and queues the rest itself.

- **Non-engine shards:** same rule: one task per worker (3 vCPU / 3 GiB), ≤ 2 in flight in total.
- **Threads:** set `OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `MKL_NUM_THREADS` and `NUMEXPR_NUM_THREADS` to 2, plus
  `MALLOC_ARENA_MAX=2`. JVM: `-XX:ActiveProcessorCount=2 -XX:MaxRAMPercentage=70`.
- **Shard size:** aim for shards of ≥ 2 CPU-minutes, so per-task start-up is negligible.
- **More or bigger workers** are an operator change (`platform/substrate/workerpools.yaml`); ask, don't improvise.

## 7. Observability and debugging

- **Task output:** OpenObserve stream `k3s_logs`, filter `k8s_namespace_name = 'ax-workers'`, or
  `kubectl -n ax-workers logs <worker-pod>`.
- **Worker state:** `kubectl -n ax-workers get workerpools,pods -o wide`.
- **Typical failures:**
  - image pull error → package not public or reference missing the digest;
  - immediate exit → image lacks `/usr/local/bin/ax-task-runner`;
  - task pending → workers full or not Ready.
- **Platform health** is checked by the operator (`just verify` with admin access).
