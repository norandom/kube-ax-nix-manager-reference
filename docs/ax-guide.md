# Using AX on the kube-ax cluster

A practical guide to running AX workflows on this cluster.

**Versions:** AX v0.3.1 on Agent Substrate main `715f2daa` (v0.3.0-34), k3s 1.36, two NixOS nodes on Proxmox (4 vCPU / 8 GiB each).

## 1. How the pieces fit

```text
you ──ax CLI──► kubectl port-forward ──► ax-server (ax-system) ──► Redis (task store)
                                              │
                                     ax-controller ──► Substrate API (ate-system) ──► Postgres
                                                              │  places each actor on a random
                                                              ▼  eligible gVisor worker
                               ax-workers: compute-kube-01 (kube-01)   compute-kube-02 (kube-02)
                                              │ snapshots
                                              ▼
                                rustfs S3 10.0.0.54:9000, bucket k3s-ate-snapshots
```

- **One Task = one actor.** An actor is one sandbox running your command inside a worker pod.
  - AX v0.3.1 has no built-in fan-out.
  - To parallelise, submit N tasks (section 6). Substrate picks a worker at random for each task.
  - There is one worker per node, so the tasks spread over both nodes.
- **Sandbox: gVisor** (AX v0.3.1 hard-codes it).
  - CPU-bound code (numpy/BLAS, JVM) runs near native speed with AVX2.
  - Syscall- and I/O-heavy code is slower than in a plain container.
- **Capacity:** each worker has **3 vCPU / 3 GiB** and runs **one task at a time**. A busy worker is skipped,
  so 2 tasks run one per node; a task submitted while both are busy **fails** (AX doesn't queue).
  - AX sets no per-task CPU or memory limits.
  - For heavy jobs, give each task about one worker's worth of work, and submit roughly as many tasks as there are workers (2), or a small multiple of that.
- **Telemetry:** goes to OpenObserve at `http://10.0.0.54:40002`.
  - Logs → stream `k3s_logs`
  - Kubernetes events → `k3s_events`
  - Traces → `k3s_traces`
  - Metrics → `k3s_<metric>`
  - AX's controller and server are auto-instrumented (Go).

## 2. One-time setup on your workstation

Tools: `kubectl`, `k9s` and `ktop` are on the workstation; the `ax` CLI is built into the repo:

```bash
cd ~/Source/kube-ax-nix-manager
export PATH="$PWD/.cache/bin:$PATH"      # ax v0.3.1 (also: ko, crane)
```

### The kubectl config

Use the **restricted** `ax-deployer` config for workflows. The admin `kube-ax` config is for operating the cluster.

| Context | File | Can do |
|---|---|---|
| `ax-deployer` | `kubeconfig/ax-deployer.yaml` | port-forward to `ax-server` (all the `ax` CLI needs); read worker pods, logs and pools in `ax-workers` |
| `kube-ax` | `kubeconfig/kube-ax.yaml` | cluster-admin |

Either point the tools at it directly:

```bash
export KUBECONFIG=$PWD/kubeconfig/ax-deployer.yaml
ax ctx                     # Active Kubernetes Context: ax-deployer
```

…or merge it into `~/.kube/config` next to the admin context, and switch between them:

```bash
uv run just kube-local ax-deployer        # adds context ax-deployer and makes it current
kubectl config use-context kube-ax        # back to admin when needed
ax --context ax-deployer get tasks        # or pick the context per command
```

Regenerate the config (new token) with `uv run just ax-deployer`. To revoke the old token, first delete it with
`kubectl --context kube-ax -n ax-system delete secret ax-deployer-token`, then regenerate.

The file as generated (local only, mode 0600; this public repo holds a placeholder):

<!-- BEGIN ax-deployer kubeconfig (generated by scripts/ax-deployer.sh; refresh with scripts/ax-guide-sync.sh) -->

```yaml
# kubeconfig/ax-deployer.yaml is not in this public repository.
# Operator: `uv run just ax-handoff` renders this document with the real kubeconfig embedded
# (.cache/handoff/, local only) and copies it to the clipboard.
```

> AX v0.3.1 has **no authentication of its own**. Anyone who can port-forward to `ax-server` sees and
> controls every task. Treat this kubeconfig like a password.

## 3. Images: the one rule that matters

Every task image must:

1. **contain `/usr/local/bin/ax-task-runner`**, so build `FROM ghcr.io/norandom/ax-task-runner:v0.3.1`;
2. **be publicly pullable.** Substrate's node agent pulls task images without credentials. Private
   ghcr packages fail with an image-pull error. After the first push, set the package to *Public* under
   `https://github.com/users/norandom/packages/container/<name>/settings`;
3. **be referenced by digest** (`@sha256:…`), so every task runs exactly the image you tested.

Example for numpy/pandas (`examples/ax/Dockerfile.numpy`, `examples/ax/job.py`):

```bash
cd examples/ax
podman build --platform linux/amd64 -f Dockerfile.numpy -t ghcr.io/norandom/ax-numpy:0.1 .
podman push --digestfile /tmp/numpy.digest ghcr.io/norandom/ax-numpy:0.1
echo "ghcr.io/norandom/ax-numpy@$(cat /tmp/numpy.digest)"     # use this reference in tasks
# then make ax-numpy public once (link above)
```

The image sets `OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS` and related variables to 2, one per worker vCPU, plus
`MALLOC_ARENA_MAX=2`. Without these, numpy starts one BLAS thread per *host* CPU and oversubscribes the
worker. For Java, size the heap with `-XX:MaxRAMPercentage` and set `-XX:ActiveProcessorCount=2`.

## 4. Run one task

```yaml
# examples/ax/compute-task.yaml
apiVersion: ax.io/v1alpha1
kind: Task
metadata:
  name: compute-1
  atespace: default
spec:
  image: "ghcr.io/norandom/ax-task-runner@sha256:c1c4951ee672ef77f845b2742124f6106b300e433426fde1768381ad5d55fad7"
  command: ["sh", "-c", "echo host=$(hostname) cpus=$(nproc); time sh -c 'head -c 1073741824 /dev/zero | sha256sum'"]
```

```bash
ax apply -f examples/ax/compute-task.yaml
ax watch task compute-1          # live phase/conditions
ax get tasks                     # PHASE, ACTOR, WORKER-IP
ax describe task compute-1
ax delete task compute-1
```

- `spec.command` runs directly in the task runner. **No LLM or API key** is needed for compute tasks.
- `spec.env` passes variables to the task.
- `debug: true` enables `ax ssh` (needs the admin context, see section 8).

## 5. See where it ran

`WORKER-IP` in `ax get tasks` is the worker pod's IP. Map it to a node:

```bash
kubectl -n ax-workers get pods -o wide        # compute-kube-01-… on kube-01, compute-kube-02-… on kube-02
kubectl -n ax-workers logs deploy/compute-kube-02 --tail=50
k9s -n ax-workers                              # or: ktop
```

The task's own stdout is in OpenObserve, stream **`k3s_logs`**. Filter on
`k8s_namespace_name = 'ax-workers'` and the worker pod name.

## 6. Distribute a workflow (fan-out)

Split the work into shards, one task per shard. Each task gets `TASK_INDEX` and `TASK_COUNT`:

```bash
IMG=ghcr.io/norandom/ax-numpy@sha256:<digest>
uv run just ax-fanout matmul 4 "$IMG" python /opt/job/job.py
ax get tasks                                   # matmul-0 … matmul-3
kubectl -n ax-workers get pods -o wide         # both workers busy
for i in 0 1 2 3; do ax delete task matmul-$i; done
```

How it spreads:

- Each task lands on a **randomly chosen** worker, and with 2 workers that means roughly half per node.
- Placement is random, not round-robin. 4 tasks can land 3+1. With many small tasks it evens out.
- Only actors that fit the worker's **remaining** capacity are placed.

Sizing rules of thumb for compute-heavy work:

- **Per worker:** 3 vCPU and 3 GiB for its one task.
- **Tasks per batch:** about 2 heavy tasks, one per worker, or 4–6 medium ones. Size shards so that one shard
  ≈ 2 CPU-minutes or more; the per-task start-up cost then stays negligible.
- **More capacity:** raise `replicas` or the `resources` in `platform/substrate/workerpools.yaml`, then
  run `uv run just platform pools`. Each node has about 6.7 GiB allocatable, and the platform uses roughly
  1.5–2 GiB of it.

## 7. Suspend, resume, snapshots

```bash
ax suspend task compute-1     # checkpoint to S3 (rustfs, bucket k3s-ate-snapshots/ax/)
ax resume task compute-1      # restores on any worker (suspended -> via S3, so it may move nodes)
```

Paused (not suspended) actors stay on the node that holds their local snapshot.

## 7a. Network access from tasks

- **Allowed:** HTTPS (TCP 443) to any **public** host, for every task in atespace `default`, attached
  automatically ~1 s after start. Retry your first download for up to 60 s.
- **Blocked:** other ports, plain HTTP, your LAN and everything cluster-internal (AX's Redis/ax-server,
  Kubernetes API, Traefik).
- **Per-prefix host lists** (live since 2026-10-06, `platform/substrate/egress-routes/scoped.json`),
  chosen by task-name prefix, longest match wins, all on port 443:

  | Prefix | Hosts |
  |---|---|
  | `ousast-engine-search-exec-` | any public host |
  | `ousast-engine-search-verify-`, `-search-probe-`, `ousast-engine-pass-` | files.because-security.com |
  | `ousast-engine-replay-` | files.because-security.com, github.com |
  | any other `ousast-engine-` name | **no egress** (deny by default) |
  | any other name | any public host |

## 8. Limitations to know (AX v0.3.1 on this cluster)

| Limitation | Consequence | Workaround |
|---|---|---|
| No fan-out, retries or parallelism in AX | 1 Task = 1 actor; a failed task is not retried | `just ax-fanout`; resubmit failed shards |
| gVisor only, no per-task resources | one task per worker, 3 vCPU / 3 GiB | size shards to the worker, see section 6 |
| No auth in ax-server | the deployer kubeconfig = full AX control | keep `kubeconfig/ax-deployer.yaml` private |
| Task state in Redis without persistence | an `ax-redis` restart forgets tasks (not snapshots) | resubmit; keep task YAML in git |
| Task images must be public | private images fail to pull | public packages, digests in tasks |
| `ax ssh` tunnels into `ate-system` | not allowed for `ax-deployer` | use `--context kube-ax` for debugging |
| No `ax logs` | — | `just ax-logs TASK` (latest run's output + exit code) |
| Tasks never reach a finished phase | `Running` even after the command exits | read the exit line via `just ax-logs`, then `ax delete task`; the reaper deletes `ousast-engine-*` tasks 10 min after exit |
| A submit can fail with "no free workers available" | both workers busy, or Substrate's ~1 s "golden" copy of a new task holds one ([sandboxing](sandboxing.md#6-the-golden-copy-you-may-see-in-the-logs)) | retry after 2–5 s for up to a minute |
| `/tmp` inside a task is RAM | 1 GB in `/tmp` = 1 GB of the worker's 3 GiB | `TMPDIR=/workspace/tmp` ([sandboxing](sandboxing.md#5-where-a-tasks-files-live-measured-2026-10-06)) |
| AX keeps the old Substrate API address after the API server pod is replaced | tasks fail, ax-controller logs `dial tcp …:443: i/o timeout` | admin: restart AX ([upgrading](upgrading-substrate.md#the-one-surprise-clients-keep-the-old-api-server-address)) |

## 9. Troubleshooting

| Symptom | Check |
|---|---|
| `ax` hangs or "connection refused" | `ax tunnel list` / `ax tunnel stop`, then retry; check `kubectl -n ax-system get pods` (admin) |
| Task fails at once with "no free workers" | both workers busy or a golden copy running: retry; `kubectl -n ax-workers get pods` |
| Task stays pending | `kubectl -n ax-workers get workerpools,pods -o wide`: are workers Ready? Are they full? |
| Image pull / `ErrImagePull` in worker logs | package not public, or reference missing the digest |
| Task fails immediately | image lacks `/usr/local/bin/ax-task-runner` (not built `FROM` the runner) |
| Slow numpy | thread variables not set, or several heavy tasks on one worker |
| Platform health | admin: `uv run just verify`; `kubectl -n ate-system get pods` |
